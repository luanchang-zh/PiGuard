# Outcome

为 PiGuard Go 后端规划下一步，并把下一轮实现范围收敛为一个可以独立联调的实时监控闭环：模拟设备 → MQTT telemetry/status → Go 最新状态及低频历史 → HTTP/WebSocket 客户端。

本轮用户要求是“先规划”，交付 brief、完整目标规格和后续优先级；业务代码尚未修改。下列行为是推荐方案，待用户整体确认后再进入 Build。

# Scope

## 已核实的现状

- 当前分支为 `go后端开发`，最近一次提交完成了 Go 后端初始化。
- 已有配置加载、环境变量覆盖、SQLite 自动建六张业务表、演示设备与默认配置种子、MQTT 初次连接和 HTTP 启停。
- 业务路由已经注册，但仓储、服务和响应映射基本仍是占位实现；`/health` 已可用。
- MQTT Subscriber 尚未实际订阅；Publisher 尚未发送；WebSocket 尚未升级连接或广播。
- `model.Telemetry` 是用于历史存储的平铺结构，缺少完整采样状态、采样时间和车道元数据，不能直接代替 MQTT 消息或最新状态。
- 基线检查 `cd go-backend && go test ./...` 已通过；现有测试主要覆盖配置和健康检查，尚不能证明业务闭环可用。

## 下一轮实现范围

1. 定义 telemetry/status 的协议 DTO，与 GORM 表结构分离；校验 JSON、设备标识、协议版本和字段。
2. 实际订阅 `car/+/telemetry`（QoS 0）、`car/+/status`（QoS 1）；断线重连后恢复订阅，处理 retained 状态与无时间戳的离线遗嘱。
3. 按已登记设备维护最新遥测、在线状态、`last_seen_at` 和传感器元数据；旧消息不覆盖更新的最新状态。
4. 遥测默认 2Hz 更新最新状态，每台设备最多 1Hz 保存历史快照；数值单位与协议一致。
5. 实现设备列表、设备详情、最新状态、历史遥测四个查询接口，完成参数与错误映射。
6. 实现 `/api/v1/ws`，广播 `telemetry` 与 `device_status`；慢连接不能阻塞 MQTT 接收。
7. 提供可重复的模拟 MQTT 联调步骤和验收数据，无需真实树莓派或现成 Vue 页面。

# Acceptance examples

- A1：已登记设备发布合法 telemetry 后，最新状态包含协议规定的速度、映射距离、温度、角速度、车道与风险，并保留采样时间、来源和传感器状态；主题与 payload 设备 ID 不符、非法 JSON 或不支持的版本不会更新任何业务状态。
- A2：接收 online status 后设备列表与详情显示在线及设备元数据；接收没有 timestamp 的离线遗嘱后显示离线；MQTT 重连完成后，上行接收自动恢复。
- A3：先发送较新的遥测，再发送较旧的遥测，HTTP 最新状态和 WS 均不回退；采样时间更新但 seq 从零重启的消息仍可成为最新状态。
- A4：设备启动后尚无遥测时，state 返回明确的空值/unknown/missing；距离、车道、车速和陀螺仪超过 1 秒、温度超过 5 秒时标记 stale，故障状态与设备离线分别表示，不能把缺失或故障数据映射成正常的 0。
- A5：同一设备按 2Hz 连续发送 10 秒的合法遥测，最新状态持续更新，历史写入频率不超过 1Hz；不同设备独立计算降频，历史数值按协议单位正确映射，重复和旧消息不会重复写入。
- A6：四个查询 API 返回协议信封及真实业务数据；不存在的设备返回 HTTP 404/40401；非法时间、start 大于 end 或非法 limit 返回 HTTP 400/40001；历史查询按设备、时间范围和限制返回稳定顺序的数据。
- A7：两个 WS 客户端可以收到 telemetry 与 device_status 的统一信封；断开或持续不读取的客户端不妨碍另一客户端收取后续消息，也不阻塞 MQTT 接收；过期遥测不会作为新的正常数据推送。
- A8：平台启动和重启保持已有演示设备及期望/已报告配置版本；设备状态在新的 status 到来前视为未确认离线，最新遥测等待新消息，已保存历史仍可查询；MQTT status 中的配置版本只更新设备报告事实，不假装已收到配置成功 Ack。
- A9：可用现有 Compose Broker 和模拟发布器，在无树莓派及 Vue 页面的环境完成 telemetry/status→HTTP/WS 的联调；必要的 Go 测试、竞态检查和静态检查全部成功，异常消息不会导致进程退出。

# Constraints and invariants

- 沿用 Gin、Paho、GORM、SQLite 和既有 handler→service→repo 分层，依赖通过构造函数注入。
- `schema_version=1`，跨设备时间为 UTC RFC3339Nano；主题中的设备 ID 与 payload 必须一致。
- 不直接向外输出 GORM 模型；完整采样信息与历史快照分开表达。
- LatestState 按 `(timestamp, seq)` 进行单调更新：timestamp 优先，时间相同时仅接受更大的 seq；用于允许设备重启后的 seq 归零，避免单看 seq 永久拒收重启后的数据。
- 在线状态由 status/遗嘱维护；telemetry 仅更新接收时间和最新测量，不替代明确的离线状态。
- 新鲜度按每个传感器的 `sample_at` 计算，不把平台接收时间当采样时间；快信号 TTL 1 秒、温度 TTL 5 秒为本轮推荐默认值。
- WS 状态视图包含新鲜度元数据，陈旧值可保留用于诊断，但必须明确标记，不能伪装为当前正常值。
- 只接收已登记设备；本轮未知设备消息丢弃并记录原因，未知设备 API 返回 404。已有演示种子就是初始联调入口。
- SQLite 单写连接；每台设备历史写入间隔至少 1 秒，最新状态及推送不受该降频限制。
- 不提交、合并、推送或创建 PR；这些交付动作另按 Native 流程和用户授权处理。

# Decisions

- 用户已明确：使用 comet-native；本轮先规划 Go 后端下一步。
- 推荐先做实时监控，随后做控制闭环；依据是现有占位状态和网络规范第 69—70 节，而非重新调整整体架构。
- 推荐下一轮同时包含最低限度的 1Hz 历史写入与查询，便于 HTTP 联调，也使当前 telemetry 表真正被使用。
- 推荐以模拟 MQTT 设备及 HTTP/WS 客户端作为验收入口，真实设备和前端可在接口稳定后接入。
- 最新状态为空、时间/seq 排序、已登记设备策略、TTL 默认值、重启状态恢复及慢 WS 连接行为是本轮明确列出的拟议行为，尚待整体 Shape 确认。
- 单个 Native change 顺序推进：协议、MQTT 接入、最新状态、历史和推送共享同一数据链路，需要联合验收；拆成 Supervisor 子任务会增加跨任务状态契约和重复集成成本。本次不创建子任务或另一个开发会话。
